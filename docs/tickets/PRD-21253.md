## Product design

Per the vendor-mcp track (`references/mcp-track.md` §2.4), this is a new connector with no MSPbots-side UI. "Product design" here means: what capabilities the connector exposes to an Agent conversation, and what an operator using Claude/ChatGPT/Cursor through MSPbots Connector can ask for and get back. There are no screens to design; the "AC"s below are the connector's user-facing contract.

### Goals / Non-goals

**Goals** (MVP, this ticket):
- An Agent connected through MSPbots Connector can, for a Mailprotector tenant identified by the operator's own auth token: list and inspect accounts, domains, user groups and users; pull per-domain traffic/usage reports and per-user message stats; list, add and remove allow/block rules; read and update spam-tolerance settings (and reset them to inherited); read and update general settings; read the dashboard summary; create a new protected domain; create a user; move a user between groups; delete a user.
- Every tool call is scoped strictly to the tenant whose credentials were sent on that request (no state, no data, no derived token survives past that request) — this is the multi-tenant guarantee a shared, multi-replica service must hold (SOP §3.3/§3.4), independent of whatever access control Mailprotector's own backend applies to the auth token.
- Errors from Mailprotector (bad token, missing resource, bad input, rate limit, vendor outage) come back to the Agent as a structured, actionable result, not a crash or an opaque 500.

**Non-goals** (explicitly out of scope for this ticket; see "Scope split" for why and what to do if a real need shows up):
- Billing/Invoices (`sections/invoices.md`) — the ticket is "email security", invoices are account billing, not a security-operations task an Agent plausibly needs.
- Creating/renaming/deleting **accounts** and **user groups** — these are tenant/org-structure provisioning actions, normally done once via the Mailprotector console, not a recurring Agent task; exposing destructive account-level operations (delete cascades to all domains) without a named need is the kind of speculative capability the repo's own code-quality bar tells us to leave out.
- Bulk user import (`sections/users.md` "Import Users") — a CSV/bulk-migration workflow, not a conversational one.
- Any OAuth / SSO flow — Mailprotector authenticates with a single bearer-like token (§3 below); there is nothing to add here.

### Acceptance criteria AC1..AC20

Each AC maps 1:1 to a tool in the tech design's change list; tool names there are authoritative, these are phrased in terms of what the Agent/operator observes.

- **AC1**: Given a valid `X-Mailprotector-Auth-Token`, when the Agent asks "what accounts can I see", then it gets a list of accounts (id, name, status, created date), paginated (default 50, max 200 per page).
- **AC2**: Given a valid token and a known account id, when the Agent asks for that one account, then it gets that account's full detail, or a structured `not_found` error if the id does not exist.
- **AC3**: Given a valid token, when the Agent asks "what domains do we protect" (optionally "under account X"), then it gets a list of domains (id, name, account id, alias parent if any), paginated.
- **AC4**: Given a valid token and a domain id, when the Agent asks for that domain, then it gets that domain's detail or `not_found`.
- **AC5**: Given a valid token, when the Agent asks to add a new protected domain (optionally as an alias of an existing one, optionally under a specific account), then the domain is created and its detail is returned, or a structured error if the manager lacks permission (`unauthorized`) or the input is invalid.
- **AC6**: Given a valid token and a domain id, when the Agent asks "how has this domain's mail traffic looked the last week" (or a given date range), then it gets the blocked/spam/virus/delivered counts and the per-user breakdown for that range.
- **AC7**: Given a valid token and a domain id, when the Agent asks "what groups exist under this domain", then it gets the list of user groups (id, name, services, user count).
- **AC8**: Given a valid token and either a domain id or a user-group id, when the Agent asks "who are the users here", then it gets a paginated list of users (id, name, type, group, created date).
- **AC9**: Given a valid token and a user id, when the Agent asks for that one user, then it gets that user's detail or `not_found`.
- **AC10**: Given a valid token and a domain or user-group id plus a username, when the Agent asks to create a new user (optionally alias/mailing-list type, optionally with a password and name), then the user is created and returned, or a structured error for invalid input or missing permission.
- **AC11**: Given a valid token, a user id and a target group id, when the Agent asks to move that user to the other group, then the move succeeds and is confirmed, or `not_found` if either id does not exist.
- **AC12**: Given a valid token and a user id, when the Agent asks to delete that user, then the user is deleted and the deletion is confirmed, or `not_found` if the id does not exist. This tool is marked destructive; the Agent must be given (and must pass) an explicit user id, never a filter/"all users like X".
- **AC13**: Given a valid token and a domain id, when the Agent asks "how has mail volume looked for these users" (optionally a date range, optionally inbound/outbound only), then it gets per-user inbound/outbound summaries.
- **AC14**: Given a valid token and a domain, user-group, or user id, when the Agent asks "what's on the allow/block list here" (optionally filtered to just allow or just block), then it gets the current rule list (address, type).
- **AC15**: Given a valid token, a target (domain/user-group/user) and one or more `{address, type}` entries, when the Agent asks to add or remove allow/block rules, then the rules are added/removed and the result is confirmed. The remove path is marked destructive and requires explicit address+type pairs — never a wildcard "clear all rules".
- **AC16**: Given a valid token and a domain, user-group, or user id, when the Agent asks "what's the current spam tolerance here", then it gets the effective thresholds and which entity they are inherited from.
- **AC17**: Given a valid token and a target entity, when the Agent asks to change (or reset to inherited) the spam-tolerance thresholds, then the change (or reset) is applied and confirmed, or a structured error for invalid scores (outside 0–1000, or max < min).
- **AC18**: Given a valid token and an account, domain, user-group, or user id, when the Agent asks "what are the effective settings here" (or asks to change one or more named settings), then it gets the current list, or the change is applied and confirmed.
- **AC19**: Given a valid token, when the Agent asks "give me the dashboard summary", then it gets the manager-scoped dashboard chart data.
- **AC20 (multi-tenant isolation, platform-level, not a Mailprotector-API behaviour)**: Given two concurrent requests to this MCP service carrying two different operators' `X-Mailprotector-Auth-Token` values, when they are processed at the same time (service runs multiple replicas, no session stickiness), then each response reflects only the credential sent on that request — no cross-request leakage via a shared variable, cache, or derived client. This is the one AC that is about the connector's own code, not about Mailprotector's backend permissions (which this connector does not and cannot alter).

### Open questions

- **[已假设]** Mailprotector's API docs explicitly state only `200`/`201`/`403` for success/forbidden; `401` for a bad/expired token, `404` for an unknown id, and `422`/`400` for invalid input are not documented. This design assumes standard REST semantics for those codes (tech design §5/§7) and maps them accordingly. If real-world behaviour differs (e.g. unknown ids also return 403, or malformed XML on error), the error-mapping table in the tech design needs a follow-up fix once verified against a live account — **does not block this design**, the mapping degrows gracefully to `upstream_error` either way.
- **[已假设]** No reseller/white-label base URL is documented beyond `https://console.mailprotector.com`; this design adds an optional `X-Mailprotector-Base-Url` header (default that host) in case a branded instance exists, mirroring the SOP's convention for self-hosted/branded vendors. If every real customer only ever uses the one host, this header is harmless and simply unused — **not blocking**.
- **[不阻塞]** Whether MSP technicians will actually want AI-driven domain/user creation (write tools) versus read-only monitoring is not stated in the ticket. Both read and a conservative set of write tools are included per the vendor-mcp SOP's "name a real business need" bar (§2.7); if product/requester wants write tools removed for v1, that's a follow-up comment, not a redesign — the read tools (AC1-4, 6-9, 13-14, 16, 18-19) stand on their own.

## Tech design

### Conclusion

Build `mailprotector-mcp` from scratch following the `vendor-mcp-development` SOP's recommended Python/FastMCP structure (§9 of the SOP): one FastMCP server, a thin `httpx`-based API client that talks Mailprotector's XML API and translates it to/from JSON at the boundary, and one tools module per resource family (accounts, domains, groups/users, rules, settings/spam/stats). Credentials come in only on the `X-Mailprotector-Auth-Token` request header per request (SOP §3), never read from environment or disk. This is the only reasonable shape for a from-scratch vendor connector — see "Option analysis" for why the alternatives were rejected.

### Where the current implementation lives

Nothing exists yet. `README.md:1-2` is the entire repo content (`mailprotector-mcp@main 0e5f2ba`). There is no prior Mailprotector integration anywhere in MSPbotsAIFramework to reuse or conflict with (org-wide search, see "Current state"). The nearest sibling pattern is any other from-scratch single-vendor MCP built under this same SOP (e.g. the MSP360 connector referenced in pipeline memory) — the shape (config / api_client / server / tools/<resource>.py) is identical by construction because the SOP mandates it, not because this vendor resembles that one.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. From-scratch Python/FastMCP per SOP §9 | New repo, `httpx` client wrapping Mailprotector's XML API, FastMCP tools per resource | Matches every other vendor-mcp repo in the org; SOP's reference Dockerfile, test shape, and credential middleware apply as-is; team already knows how to operate/debug this shape | Need to hand-write XML⇄JSON translation (vendor has no JSON mode) | **Chosen** |
| B. Wrap an existing community Mailprotector client library | Use a third-party Python/Node package if one exists | Less code to write | A repo search turned up no maintained MSPbots-adjacent or well-known community client for this 2010-era API; adopting an unmaintained third-party package inside a security-sensitive, multi-tenant service is a supply-chain risk for no real savings (the API surface is small and the XML shapes are simple) | Rejected — no suitable library found |
| C. Fork/mirror `mailprotector/mailprotector-api` docs repo itself | That repo is docs + example wrapper code only (`libraries/`), not a server | It is literally not a server; the SOP also explicitly bars forking/mirroring vendor repos — new vendor connectors are always built fresh in MSPbotsAIFramework | — | Rejected — not applicable, and against SOP policy |

No framework choice to debate beyond "Python + FastMCP" — that is the SOP's documented default (§9) and there is no vendor-specific reason to deviate (no existing codebase, no special runtime requirement).

### Data & API contract

Transport (MCP side, SOP §1, unaffected by vendor choice): `POST /mcp` (Streamable HTTP, stateless), `GET /health` → `{"status": "ok"}`.

Credential headers (SOP §3.1 naming convention):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Mailprotector-Auth-Token` | Yes | Per-manager authentication token; sent as the HTTP Basic username (dummy password) to the Mailprotector Console API | Mailprotector Console → "Edit Profile" screen |
| `X-Mailprotector-Base-Url` | No | Override for a branded/self-hosted console; default `https://console.mailprotector.com` | — |

Missing `X-Mailprotector-Auth-Token` → `401` with body listing the required header (SOP §3.2), before any outbound call to Mailprotector.

| Tool | Method + path | Key params | Returns (trimmed) |
|---|---|---|---|
| `mailprotector_list_accounts` | `GET /accounts.xml` | `limit≤200 (default 50)`, `offset` | `[{id, name, account_status, created_at}]` |
| `mailprotector_get_account` | `GET /accounts/{id}.xml` | `account_id` | `{id, name, account_status, created_at}` |
| `mailprotector_list_domains` | `GET /domains.xml` or `GET /accounts/{account_id}/domains.xml` | `account_id?`, `limit`, `offset` | `[{id, name, account_id, parent_id}]` |
| `mailprotector_get_domain` | `GET /domains/{id}.xml` | `domain_id` | `{id, name, account_id, parent_id}` |

`create`/`update`/`set` request bodies are built from the tool's typed args into the vendor's documented XML shape (examples in `mailprotector-api/sections/*.md`); responses are parsed back to the trimmed JSON shapes above — never the vendor's raw XML string.

Error mapping (SOP §4.2 vocabulary; vendor docs only state `200`/`201`/`403` explicitly — see Open Questions "[已假设]" for the rest):

| Mailprotector status | code | retryable |
|---|---|---|
| 401 (assumed) | `unauthorized` | false |
| 403 (documented) | `unauthorized` | false |
| 404 (assumed) | `not_found` | false |
| 400/422 (assumed) | `invalid_argument` | false |
| 429 (assumed, not documented but handled defensively) | `rate_limited` | true |
| 5xx / connect or read timeout / XML parse failure | `upstream_error` | true |

`list`/`search` tools return an empty array on no match, never `not_found` (SOP §4.2); `not_found` only when a specific id was requested and the vendor returned 404/403-for-missing (observed behaviour to confirm once a live token is available — see Open Questions).

Backward compatibility: not applicable, first version of a new service — no prior contract to preserve.

### Key flow / sequence

Representative flow for AC14/AC15 (read then update an allow/block list):

```
Agent -> Gateway: tools/call mailprotector_list_allow_block_rules(scope_type=domain, scope_id=545)
Gateway -> mailprotector-mcp: POST /mcp (X-Mailprotector-Auth-Token: <tenant token>)
mailprotector-mcp -> middleware: read token into ContextVar
mailprotector-mcp -> api_client: GET https://console.mailprotector.com/domains/545/allow_block_rules.xml (Basic <token>:X)
api_client -> Mailprotector: HTTP GET
Mailprotector -> api_client: 200, XML <rules>...</rules>
api_client -> tool: parsed [{address, type}, ...]
tool -> Gateway -> Agent: JSON string result
middleware: ContextVar reset (finally)

Agent -> Gateway: tools/call mailprotector_set_allow_block_rules(scope_type=domain, scope_id=545, rules=[{address: "spam.example.com", type: "block"}], action=add)
... same path, POST /domains/545/allow_block_rules.xml with the XML <rules><rule>...</rule></rules> body ...
Mailprotector -> api_client: 200
tool -> Gateway -> Agent: {"status": "ok", "applied": 1}
```

Every tool call is one Gateway request → one Mailprotector API call (or, for the `set_allow_block_rules` "add" path, one call carrying all the rules in a single request body per the vendor's documented batch support) → one response. No multi-step orchestration, no background jobs, no local state kept between calls.

### Non-functional

- **Idempotency & concurrency**: credential and derived-client state live only in a request-scoped `ContextVar`, reset in `finally` (SOP §3.3) — this is what makes AC20 hold under concurrent, multi-tenant, multi-replica traffic. `mailprotector_move_user` and `mailprotector_set_spam_tolerance` are marked `idempotentHint=True` (repeating them with the same args is safe); `mailprotector_create_domain`/`create_user` are not (repeating creates a duplicate — the vendor API has no upsert-by-name semantics documented). `mailprotector_delete_user` and the "remove" path of `mailprotector_set_allow_block_rules` are marked `destructiveHint=True` and only accept explicit ids/addresses (SOP §2.7) — no filter-based bulk delete exists in this tool set.
- **Performance**: this is a thin passthrough; the vendor API's own list defaults (`limit` 50, hard cap 200 — SOP §2.5) are mirrored on every `list` tool, and `mailprotector_get_user_message_stats`/`get_domain_traffic_report` similarly cap result size and truncate with `has_more` if a response would exceed 20,000 characters (SOP §2.5). Outbound calls: 5s connect / 30s read timeout, limited retries with backoff on 429/5xx (SOP §5); total tool-call time budget < 120s including retries.
- **Security**: credentials never touch config, logs, or disk (SOP §3.1/§11); request-level isolation via `ContextVar` (above); no cross-request caching of tokens or derived data (SOP §3.4) — every call re-authenticates against Mailprotector, trading a little latency for the actual multi-tenant safety guarantee this service must hold. Mailprotector's own authorization ("what can this manager's token see") is out of this connector's control and is not re-implemented or second-guessed here — AC20 is about the connector's code, not about the vendor's access model.
- **Multi-tenant isolation**: the vendor API already scopes every response to "what this manager's token is allowed to see" — this connector does not add its own tenant model, it passes the caller's token straight through (one token per request, no mixing). The one place this connector could introduce a leak is accidentally reusing a client/token across concurrent requests, covered above and tested by `tests/test_middleware.py`'s concurrency case (AC20).
- **Observability**: structured (JSON) logs per request: tool name, redacted arg summary, Mailprotector path + status code, latency, error `code` if any (SOP §6). No token, no raw response body, ever logged.

## Decisions made by DEV01

(Per `references/mcp-track.md` §2.4 — choices made without a human to ask, posted as a separate `[DESIGN DECISIONS]` comment after the `[DESIGN]` stub.)

- **Excluded Invoices/billing, account/user-group create-update-delete, and bulk user import from v1** — why: the ticket names no concrete need for any of these, and they are either billing-adjacent (out of an "email security" scope) or one-time provisioning actions normally done once via the console, not a recurring Agent task; alternative not chosen: build the full API surface 1:1 (would exceed the SOP's ≤20 tool guidance and expose destructive account-level operations with no stated justification per SOP §2.7).
- **20 tools, scope-parameterized (`scope_type` + `scope_id`) instead of one tool per domain/user_group/user variant** — why: the vendor API itself offers the same operation (list users, allow/block rules, spam tolerance, settings) against three or four different parent types; collapsing these into one tool with a `scope_type` enum keeps the tool count at the SOP's ≤20 target and matches SOP §2.1's explicit guidance to merge "same capability, different parameter" tools; alternative not chosen: one tool per scope type (would have produced 30+ tools for the same capability set).
- **Assumed standard REST status-code semantics (401/404/422/429) beyond the vendor's documented 200/201/403** — why: no test account exists to verify live behaviour at design time, and the vendor docs are silent on the rest; alternative not chosen: blocking the ticket on this gap (rejected — the fallback `upstream_error` bucket makes the assumption safe to proceed on, and it's a correctable follow-up, not a redesign).
- **Added an optional `X-Mailprotector-Base-Url` header, defaulting to `console.mailprotector.com`** — why: mirrors the SOP's convention for vendors that might have a branded/self-hosted instance, costs nothing if unused; alternative not chosen: hardcoding the host (would break on day one if a branded reseller instance turns out to exist).
- **Chose stdlib `xml.etree.ElementTree` over `xmltodict`/`lxml`** — why: the vendor's XML shapes are flat and simple (see fixtures in `sections/*.md`), stdlib is sufficient and keeps the dependency surface minimal (SOP §2.1-adjacent code-quality bar: prefer what's already available before adding a dependency); alternative not chosen: `xmltodict` (would be marginally more convenient for nested arrays, not needed here).
