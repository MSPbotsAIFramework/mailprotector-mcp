### Fixes

1. [must-fix #1] Added structured per-request logging (SOP §6), invoked from the single choke point `runtime.call_api` so all 20 tools get it without touching any of the five tool modules:
   - New `src/mailprotector_mcp/logging_config.py`: `logging.getLogger("mailprotector_mcp")` with a JSON-lines `StreamHandler` (`configure_logging()`, idempotent, called once from `__main__.py` before `create_app()`); `redact_args`/`_redact_value` (masks any arg whose name contains password/token/secret/credential/auth; truncates long strings to 60 chars; summarizes lists/dicts to a bare count instead of their contents, since rules/settings lists can carry customer addresses); and `log_tool_call`, which emits one JSON object per call: `ts`, `request_id`, `tool`, `args` (redacted), `mailprotector_path`, `status_code`, `error_code`, `latency_ms`.
   - `runtime.call_api` (`src/mailprotector_mcp/runtime.py`) now identifies the calling tool via `sys._getframe(2)`: every tool's body is the direct statement `return await call_api(_call)`, so the frame two levels up from the helper `_caller_tool_name_and_args` is always that tool function's own frame (`co_name` for the tool name, `f_locals` filtered to the function's own parameter names for the args) -- this is what lets one change cover all 20 tools without editing any tool file. It times the call and logs on every exit path (`not_configured` before any HTTP attempt is made; success; `MailprotectorAPIError`), and never passes the auth token or a parsed response body into the logger -- only `client.last_call`'s path/status and the mapped `error_code` (`errors.code_for_status`).
   - `api_client.py`'s `MailprotectorClient` gained `self.last_call` (method/path/status_code of the most recent HTTP attempt; set on every branch of `_request` -- success, retryable intermediate attempt, final failure, and transport/timeout errors with `status_code=0`). This is how `call_api` learns "the Mailprotector path + status code" without `_request` needing to know anything about logging.
   - `server.py`'s `CredentialMiddleware` now also assigns `runtime.request_id_var` (`uuid4().hex[:12]` per inbound HTTP request, same set/reset-in-`finally` discipline as the existing credential ContextVars) so every tool call made within one request shares one correlation id. The tech design's Observability line doesn't name a request-id explicitly, but SOP §6 does ("带 request-id / 关联 id"), and the service already had the exact per-request ContextVar mechanism to extend for it.
   - `__main__.py` calls `configure_logging()` once at import time, before `create_app()`.
   - The round-1 finding also noted this gap wasn't flagged in Self-test (unlike the one other known gap, which was). This Fixes section, plus the "Logging" evidence below, is that disclosure for this round.
